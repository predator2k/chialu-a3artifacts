## summary
This clause fixes language-level rules for intermediate/final rounding, parameters, return values, preferred widths, and value-changing optimizations. Expression evaluation rules determine operation order, intermediate formats, destination formats, and whether assignment involves one or two roundings.

## other_normative
* **Informative:** A language expression-evaluation rule encompasses operation order, implicit-intermediate formats, one-rounding versus two-rounding assignments, generic/non-generic parameter formats, and generic-operation result formats. # p.59
* **Should:** A language standard that permits multiple expression-evaluation rules or implementation-defined additional rules should define preferredWidth attributes. # p.59
* **Should:** Language standards should disallow, or provide warnings for, mixed-format operations whose implicit conversions might change operand values. # p.59
* **Should:** A language standard that defines generic operations, supports more than one arithmetic format in a radix, and defines or permits multiple mappings from expressions to standard operations should define user-enabled preferredWidth attributes for that radix. # p.60
* **Should:** Each such language standard should define, and require implementations to provide, a means to specify preferredWidthNone for a block. # p.60
* **Should:** Each such language standard should define, and require implementations to provide, a means to specify preferredWidthFormat for a block. # p.60
* **Informative:** Table 10.1 identifies addition, subtraction, multiplication, division, squareRoot, fusedMultiplyAdd, minNum, maxNum, minNumMag, maxNumMag, and Clause 9 functions as suitable for preferredWidth attributes. # p.60
* **Should:** Language standards should define literal source-code meaning through operation order, implicit/explicit destination formats, and the scope of attribute or dynamic-mode specifications. # p.61
* **Should:** A language standard should require implementations, by default and without enabled optimizations or alternate exception handling, to preserve literal meaning without transformations that change numerical results or raised flags. # p.61
* **Informative:** Literal meaning is preserved by retaining defined operation order/destination formats and by applying commutative/associative/distributive/identity laws only when numerical results, result representations, and flags are preserved. # p.61
* **Informative:** Literal meaning also requires preserving the ordering of operations affected by attributes/dynamic modes relative to modifications of those modes, and preserving flag-changing operations relative to flag tests or saves. # p.61
* **Informative:** Permitted transformations include replacing `0 + x` when `x` is nonzero and not a signaling NaN and the result has the same exponent as `x`; replacing `1 × x` when `x` is not a signaling NaN and the result has the same exponent as `x`; changing a quiet NaN’s payload or sign; changing the order in which different flags are raised; and changing how many times a flag is raised when it is raised at least once. # p.61
* **Should:** A language standard should define, and require implementations to provide, block-scoped attributes that separately or collectively allow/disallow value-changing optimizations. # p.61
* **Informative:** Value-changing optimizations may include associative/distributive transformations, synthesis of fusedMultiplyAdd from multiplication plus addition, synthesis of formatOf from an operation plus result conversion, and wider intermediate results. # p.61

## model_gaps
* The model has no expression-evaluation or destination-typing layer for implicit intermediate formats, preferredWidth attributes, stored-value substitution, or language-defined parameter/return formats. The gap affects bit-exact results when widening or double rounding changes a value. # p.59
* The model has no status flags, so it cannot verify requirements or optimization permissions based on which flags are raised, their ordering, or their multiplicity. The gap does not prevent checking numerical bits where the permitted transformation also preserves the numerical result. # p.61
* The model has one NaN without signaling/quiet, payload, or sign distinctions, so it cannot test the signaling-NaN preconditions or permitted quiet-NaN payload/sign changes. The gap can affect whether an identity transformation is permitted and prevents IEEE bit-exact NaN representation checks. # p.61

## open_questions
* The target programming language’s expression-evaluation rules must specify operation order, implicit intermediate formats, assignment rounding count, and generic-operation parameter/result formats. # p.59
* The target programming language must specify which Table 10.1 operations are affected by preferredWidthFormat and how “typically” is resolved. # p.60
* The target programming language must specify the available value-changing-optimization attributes and their scopes. # p.61
