## summary
The paper experimentally determines the undocumented arithmetic behavior of NVIDIA V100, T4, and A100 tensor-core matrix multiply-accumulate units. The low-precision modes use exact products, round-towards-zero accumulation, final-only normalization, and magnitude-ordered summands, while A100 binary64 behaves like IEEE 754 elementary arithmetic. # p.8-16

## families
### tensor_core_mixed_precision_mac  (role: analyzes)
mechanism: Each output element adds C to a tensor-core dot product. V100/T4 low-precision modes and A100 binary16/bfloat16/TensorFloat-32 modes retain full-precision products, align summands relative to the largest-magnitude operand, truncate additions toward zero, retain carry headroom without normalizing partial sums, and normalize only the final result. A100 binary64 instead rounds to nearest with ties to even and normalizes after every addition. # p.8-15
choices:
  dot_width_per_pe: 4 (V100/T4); 8 (A100 binary16/bfloat16/TensorFloat-32); 2 [outside domain] (A100 binary64)   # p.2
  partial_sum_rounding: truncate_toward_zero (V100/T4 low-precision modes and A100 binary16/bfloat16/TensorFloat-32); rne (A100 binary64)   # p.10, p.14-15
  alignment_target: largest_magnitude [outside domain] (all tested modes except A100 binary64)   # p.9, p.15
  subnormal_support: true (V100/T4 binary16/binary32 and tested A100 low-precision modes)   # p.7-8, p.14-15
new_choices:
  product_handling: exact_full_precision — binary16 products are retained exactly rather than rounded to binary16   # p.8-9, p.15-16
  partial_sum_normalization: final_only (low-precision modes); after_each_addition (A100 binary64) — when accumulator normalization occurs   # p.11-12, p.15
  accumulator_bottom_bits: 0_extra (V100); 1_extra (T4 and equivalent A100 low-precision modes) — precision below the binary32 significand   # p.14-16
  carry_headroom_bits: at_least_2, most_likely_3 — upper significand bits retained because partial sums are not normalized   # p.12-13
  final_normalization_rounding: round_towards_zero — rounding used when the low-precision-mode accumulator is converted to binary32   # p.13
slots:
  none
parameters: V100/T4 use 4 product terms plus C per output; A100 uses k=8 for binary16/bfloat16/TensorFloat-32 and k=2 for binary64. V100/T4 accept binary16 products with binary16 or binary32 accumulation output; A100 also supports bfloat16/binary32, TensorFloat-32/binary32, and binary64/binary64. Latency and II are UNKNOWN. # p.2, p.6, p.14

errors_and_checks: Binary16 products are exact, but each output can contain four accumulation rounding errors. # p.8-9 The accumulator has no alignment guard digits on V100, and the paper demonstrates relative error 1 for one cancellation case. # p.11 Final-only normalization causes non-monotonic results: increasing c11 from 1 − 2−24 to 1 changes the output from 1 + 2−23 to 1. # p.13-14 No hardware fault checker or detection coverage is evaluated.
conditions: The conclusions rely on designed test cases and the assumption that hardware behavior is consistent across the input space. # p.6 The tested devices are Tesla V100 SXM2 16GB with CUDA 10.1, Tesla T4 16GB with CUDA 10.1, and A100-PCIA 40GB with CUDA 11.1. # p.4 The low-precision findings do not apply to A100 binary64, which normalizes after every addition, uses round-to-nearest ties-to-even, avoids the reported non-monotonicity, and does not always start with the largest addend. # p.15

## space_gaps
* `tensor_core_mixed_precision_mac.dot_width_per_pe` needs value 2 for the A100 binary64 tensor-core operation. # p.2
* `tensor_core_mixed_precision_mac.alignment_target` needs `largest_magnitude`, which is the ordering established for the tested low-precision modes. # p.9
* The family lacks choices for partial-sum normalization, accumulator bottom precision, carry headroom, exact-product retention, and final-normalization rounding. # p.8-13

## open_questions
* The experiments prove at least two carry-headroom bits, but the third bit and the resulting 27-bit V100 width depend on an alignment-placement assumption. # p.12-13
* The binary16 output-conversion test excludes round-towards-zero but does not uniquely distinguish round-to-nearest from round-towards-plus-infinity. # p.10-11
* The accumulation order after the largest-magnitude summand is not determined. # p.9, p.13
* The A100 binary64 addition order is not established beyond the finding that it does not always begin with the largest addend. # p.15
