## summary
This specification defines MX-compliant block formats, binary interchange encodings, and basic operations. Each MX block combines one shared scale with 32 floating-point or integer elements. The specification fixes concrete format parameters, decoding, conversion, rounding, saturation, and dot-product semantics while leaving some algorithms and intermediate precision implementation-defined.

## other_normative
* A data format represents one or more real values, positive/negative infinities, or quiet/signaling NaNs; “data type” and “data format” are interchangeable terms. # p.6
* This specification does not differentiate quiet NaNs from signaling NaNs. # p.7
* `ExMy` denotes a scalar format with one sign bit, `x` exponent bits, and `y` mantissa bits; when `y` is zero, as in E8M0, the format has no sign bit. # p.7
* “must” marks an absolute compliance requirement, “should” marks a recommendation, and “may” marks an optional action. # p.7
* An MX-compliant format contains a scale `X`, `k` private elements `Pᵢ` of one data type/width, and a scaling block size `k`; its encoded size is `w + kd` bits. # p.8
* Physical-memory layout is not prescribed. Repeated scales may be compressed/pruned, and a scale may be stored contiguously with or separately from its elements. # p.8
* Table 1 fixes `MXFP8` as FP8 E5M2 or E4M3 elements with `d=8`, `k=32`, E8M0 scale, and `w=8`. # p.9
* Table 1 fixes `MXFP6` as FP6 E3M2 or E2M3 elements with `d=6`, `k=32`, E8M0 scale, and `w=8`. # p.9
* Table 1 fixes `MXFP4` as FP4 E2M1 elements with `d=4`, `k=32`, E8M0 scale, and `w=8`. # p.9
* Table 1 fixes `MXINT8` as INT8 elements with `d=8`, `k=32`, E8M0 scale, and `w=8`. # p.9
* MX format names prepend `MX` to the element data-type name. # p.9
* An implementation may support any subset of concrete MX formats, but each supported format must use all parameters in Table 1; alternative element encodings count as different formats. # p.9
* E4M3 has zero `S 0000 000₂`, maximum normal `S 1111 110₂ = ±2⁸ × 1.75 = ±448`, minimum normal `S 0001 000₂ = ±2⁻⁶`, maximum subnormal `S 0000 111₂ = ±2⁻⁶ × 0.875`, and minimum subnormal `S 0000 001₂ = ±2⁻⁹`. # p.10
* E5M2 has zero `S 00000 00₂`, maximum normal `S 11110 11₂ = ±2¹⁵ × 1.75 = ±57,344`, minimum normal `S 00001 00₂ = ±2⁻¹⁴`, maximum subnormal `S 00000 11₂ = ±2⁻¹⁴ × 0.75`, and minimum subnormal `S 00000 01₂ = ±2⁻¹⁶`. # p.10
* FP8 implementations must adhere to the OCP 8-bit Floating Point Specification and support both SAT and OVF conversion methods with an overflow attribute that selects the method. # p.10
* E2M3 has zero `S 00 000₂`, maximum normal `S 11 111₂ = ±2² × 1.875 = ±7.5`, minimum normal `S 01 000₂ = ±2⁰ × 1.0 = ±1.0`, maximum subnormal `S 00 111₂ = ±2⁰ × 0.875 = ±0.875`, and minimum subnormal `S 00 001₂ = ±2⁰ × 0.125 = ±0.125`. # p.11
* E3M2 has zero `S 000 00₂`, maximum normal `S 111 11₂ = ±2⁴ × 1.75 = ±28.0`, minimum normal `S 001 00₂ = ±2⁻² × 1.0 = ±0.25`, maximum subnormal `S 000 11₂ = ±2⁻² × 0.75 = ±0.1875`, and minimum subnormal `S 000 01₂ = ±2⁻² × 0.25 = ±0.0625`. # p.11
* E2M1 has zero `S 00 0₂`, maximum normal `S 11 1₂ = ±2² × 1.5 = ±6.0`, minimum normal `S 01 0₂ = ±2⁰ × 1.0 = ±1.0`, maximum subnormal `S 00 1₂ = ±2⁰ × 0.5 = ±0.5`, and minimum subnormal `S 00 1₂ = ±2⁰ × 0.5 = ±0.5`. # p.12
* INT8 uses two’s-complement encoding with an implicit `2⁻⁶` scale, one sign bit, one integer bit, and six fractional bits. # p.12
* The INT8 maximum negative representation `(−2)` may be unused to maintain positive/negative symmetry and avoid negative bias. # p.12
* INT8 has zero `0 0.000000₂`, symmetric maxima `0 1.111111₂ = +1 63/64` and `1 0.000001₂ = −1 63/64`, and minimum magnitudes `0 0.000001₂ = +1/64` and `1 1.111111₂ = −1/64`. # p.13
* E8M0 is an unsigned biased Float32 exponent with bias 127, supported exponent range `-127 to 127`, no infinity or zero encoding, and the sole NaN encoding `11111111₂`. # p.13
* A minimally supported MX dot product factors both shared scales outside the element-product reduction. # p.13
* A power of two means `2ⁿ`, where `n` is a positive integer, negative integer, or zero. # p.14
* Other scalar-vector-to-MX conversion algorithms may be supported. # p.14

## model_gaps
* The model’s binary-float tuple cannot directly represent E4M3’s finite values in the all-ones exponent field because the tuple normally associates special encodings with exponent structure; this affects bit-exact E4M3 encoding unless explicit encoding rules are added. # p.10
* The model has one NaN and therefore matches this specification’s lack of quiet/signaling distinction, but it must preserve the multiple FP8 NaN bit encodings where interchange bits are checked. # p.10
* The model does not describe configurable SAT/OVF conversion attributes; this affects bit-exact overflow results for FP8 and any optional alternative overflow methods. # p.11
* The model’s conventional signed-integer representation does not include INT8’s implicit `2⁻⁶` scale or the option to leave the most-negative code unused; both affect bit-exact interpretation and conversion. # p.12
* The model’s binary-float representation includes a significand and optional Inf/NaN support, but E8M0 is an unsigned exponent-only scale with no zero or infinity; a separate E8M0 encoding is required for bit-exact blocks. # p.13
* The model does not intrinsically represent an MX block’s shared scale, block size, or rule that a NaN scale overrides all element encodings; these affect every decoded block value. # p.8
* The model does not specify implementation-defined intermediate precision or reduction order for dot products, so the specification does not determine a single bit-exact dot-product result without an implementation profile. # p.14
* The model has no flags or traps, which does not lose specified behavior because this clause defines none. # p.11

## open_questions
* The specification incorporates FP8 requirements by reference, so FP8 behavior not reproduced in Tables 2 and 3 requires the cited OCP FP8 specification rather than inference.
* The scalar-vector conversion algorithm does not define `X` when every input magnitude is zero.
* The scalar-vector conversion algorithm does not specify how its computed scale is rounded, clamped, or encoded when the exact scale is outside E8M0’s finite exponent range.
* The binary encoding of elements when the block scale is NaN is explicitly outside scope and must not be inferred.
* The text’s “maximum negative representation of −2” is incomplete or ambiguous as printed; an implementer must not infer the intended exponent or bit pattern.
* Dot-product internal precision and operation order are implementation-defined, so a conformance profile is needed for one reproducible bit-exact result.
* Conversion from NaN to FP6, FP4, and INT8 is implementation-defined, so a conformance profile must select the result.
