# Plan dumps — what a plan actually changes

Generated by `dump_plans.py` (in this folder) against the chialu submodule.

A **plan** is a datapath sharing scheme over a *fixed* structure set. `AluFloat.register_op`
(`chialu/targets/rtl/alu_float.py:571`) builds a mode's structures from its format and its op
list alone — it reads no binding and no family choice — so every plan of one target sees the
same manifest, and the only thing a plan varies is which structures are realized by one
physical unit. That is why each file below prints the manifest once and then, per plan, only
the groups.

| file | target | structures | plans | free micro-architecture variables |
|---|---|---|---|---|
| [`fp_alu_cmp_plans.md`](fp_alu_cmp_plans.md) | `targets/eval/fp_alu_cmp_plans.yaml` | 24 | 4 | 9 |
| [`mixed_cvt_alu.md`](mixed_cvt_alu.md) | `targets/mixed_cvt_alu.yaml` | 32 | 64 | 11 |
| [`int_subword_alu.md`](int_subword_alu.md) | `targets/int_subword_alu.yaml` | 24 | 144 | 18 |

Each `.md` carries the manifest table, the free variables, and the plans (evenly spread through
the enumeration, with each plan's JSON in a collapsed block). The matching `.plans.json` has the
same content machine-readable, with *all* plans rather than the shown subset.

## The two ways a plan constrains the micro-architecture

Both were found by the sampler drawing illegal designs, and both are now handled in
`harness.py`:

1. **The plan pins a family.** A sharing group does not merely group its members — for some
   kinds it requires the family that *implements* that sharing. `chialu/plans.py:387`
   (`SHARING_FAMILY`) maps `multiplier → twin_precision_subword`, `logic → wide_gate_row`,
   `rounder`/`unpacker` → `shared_across_formats`, and `plan_vars` writes those. The column
   "family the sharing requires" shows them. Sampling those variables contradicts the partition
   and the render refuses the design.

2. **The plan ties variables together.** For the arithmetic kinds `SHARING_FAMILY` is `None` —
   there the family *is* a micro-architecture, not a sharing pattern. But a shared group is
   still one module, so its members must declare *one* family:
   `chialu/targets/rtl/families/partition.py:94` refuses a group whose members chose
   differently ("physical sharing is not implemented for these selected structures"). So a
   group is exactly **one** micro-architecture decision, and the sampler draws it once per
   group. The column shows these as "— (a micro-architecture: one draw per group)", and the
   per-plan line reports how many variables are tied this way.

The practical consequence for the search: **a plan does not only choose sharing, it changes the
size of the micro-architecture space.** `fmt-all` on `fp_alu_cmp` ties 6 of the 9 free variables
into 3 group decisions and pins 6 more, so its space is far smaller than `fmt-none`'s.

## Note on `fp_fma`

`fp_fma` structures exist in every float mode (they carry `fadd,fsub,fmul`) but appear in no
group of any enumerated plan: the fused families are only renderable under a partition that
groups the fma with its adder and multiplier, and `sharing_schemes` does not enumerate that
grouping. This is the open `fused_fma` question recorded in `handoff_0920.md` §12.
